# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A patcher script (`patch.ts`) that modifies the Claude Code VS Code extension to add:
- **Persistent sessions sidebar** — converts the floating sessions dropdown into a fixed side panel styled like a native VS Code view; drag the divider to resize it (width is remembered, double-click resets)
- **Live status dots** — colored indicators on each session (green=done, blue=running, orange=waiting, gray=seen)
- **Include Selection default off** — the open file / selected lines are not attached to prompts unless you opt in, per session (dimmed chip in the input footer, click to attach)
- **Reasoning effort default max** — sets effort to "max" on every new session
- **Drafts kept per session** — text, @-mentions and attachments you haven't sent survive switching sessions; an existing session's text also survives a window reload (2.1.300+ keeps text and attachments itself; the patch adds the rest)
- **Phone remote** — a **Connection** tab next to Local and Web in the sessions panel connects the Mac to Tailscale, so the CCE Remote web app (`remote-app/`) can list every open window's sessions, mirror them live, answer their prompts and send messages from a phone. The bridge (`remote-bridge/`) is copied into the extension as `cce-remote/` and hooked into `extension.js`; it stays off until "Connect with Tailscale"
- **Claude in Chrome auto-accept** — an opt-in switch in the Connection tab (off by default; remote access on or off). While it is on, the bridge answers Claude in Chrome's routine permission prompts in VS Code itself, as Allow would. A site card gets its "always allow this site" for the session; any other Claude in Chrome prompt gets a plain allow. Prompts that Claude Code marks for a person (`defaultToNo`, a safety check's `reason`, a hook's ask) still ask

It auto-detects and patches all installed editors (VS Code, VS Code Insiders, Cursor, VSCodium).

Separately, `claude-commit/` is a small companion VS Code extension (not a patch): a **Generate Commit Message with Claude** button for the Source Control view that does what the built-in ✨ Copilot button does, answered by Claude Haiku through the user's Claude Code login. `patch.ts` installs it into the editors it patches (`--revert` removes it, `--no-commit-button` skips it). `bun run claude-commit/install.ts` manages it on its own.

## Running

```bash
# Apply patch (Bun recommended); also installs the claude-commit button
bun run patch.ts

# Revert (also uninstalls the button)
bun run patch.ts --revert

# Patch without touching the button
bun run patch.ts --no-commit-button

# Patch without the phone remote (no hook, no cce-remote/, no Connection tab)
bun run patch.ts --no-remote

# Alternative with Node.js
npx tsx patch.ts
npx tsx patch.ts --revert

# claude-commit tests
bun test claude-commit/test

# phone remote tests: the bridge and the patch hooks, then the web app (npm ci first: its tests use its dependencies)
bun test remote-bridge/test
(cd remote-app && npm ci && bun test test && npm run build)
```

To try the patch without touching the installed editors, run it with `HOME` pointing at a scratch folder that holds copies of the extension (`<scratch>/.vscode-insiders/extensions/anthropic.claude-code-<version>-darwin-arm64/` with `extension.js`, `webview/index.js`, `webview/index.css`, `package.json`): `HOME=<scratch> bun run patch.ts --no-commit-button`.

After patching, restart each editor with `Reload Window`. The commit button's move into the commit message box needs a full restart (`argv.json`).

## Architecture

The patcher is a single file, `patch.ts`; the phone remote's hooks live in `remote-bridge/install.ts`, which it imports (as it imports `claude-commit/install.ts`). No build step, no dependencies beyond the runtime.

### Patch pipeline (executed per editor)

1. **`patchExtensionJs`** — Hardcodes `sessionsListEnabled` and `primaryEditorEnabled` feature flags to `true` in `extension.js`
2. **`patchWebviewJs`** — Modifies `webview/index.js`: removes the isOpen guard, replaces the overlay backdrop with a `.cce-sash` resize handle (it sits between the chat column and the panel), forces isOpen=true (the mount passes an expression, `isOpen:z&&!q`, since 2.1.281), builds the sessions list unconditionally (2.1.309 builds it only while the dropdown is open: `localSessions:z?…:[]`), no-ops onClose. **`appendResizeScript`** then appends the drag logic (event delegation on `.cce-sash`, width in the `--cce-sessions-w` CSS variable + localStorage)
3. **`patchIncludeSelectionDefault`** — Flips `useState(!0)` to `useState(!1)` for the includeSelection state owner. 2.1.280+ removed that toggle, so it falls back to **`patchSelectionOptIn`**: a per-session `cceSelOn` signal (off), `send()` gated on it, the chip's × turns it off, and the footer renders the chip dimmed until clicked
4. **`patchDefaultEffortMax`** — Changes the `effortLevel` observable default from `void 0` (Auto) to `"max"` in `webview/index.js`
5. **`patchExtensionEffortMax`** — Makes `extension.js` pass `--effort max` to the CLI by default (unless explicitly overridden). Since 2.1.296 the SDK builds the flag as `FLAG("--effort",value)` → `--effort=value`. This is what makes sessions run at max: the webview default from step 4 only sets what the picker shows until the CLI reports its level
6. **`patchSessionStatusDots`** — Injects status computation code and a `<span class="cce-status-dot">` element into the session item renderer
7. **`patchDraftPersistence`** — The chat view is keyed by the session's `internalId`, so switching sessions remounts it and drops the input's text/@-mention state and the chat view's attachments state. Seeds those states from `session.cceDraft` and saves every change back via effects (a send empties both, which clears the draft); the text is written back into the contentEditable on mount, caret at the end on first focus. Existing sessions' text is mirrored to localStorage (`cce-draft:<sessionId>`, pruned after 30 days). The `window.__cceDraft` runtime is prepended to the bundle. 2.1.300+ keeps text (`session.composerDraft`, restored on mount with the caret at the end) and attachments (`session.composerAttachments`) itself, so there **`patchComposerDraft`** only adds what upstream lacks: the @-mention set and the localStorage mirror. The runtime puts a stored draft into `composerDraft` before the input reads it, so upstream's restore applies after a reload too
8. **`patchWebviewCss`** — Restyles the dropdown as a fixed sidebar, hides the overlay, makes the body a horizontal flex container. **`patchSessionsPanelCss`** adds the VS Code look (theme tokens only, scoped to the panel so the Session Manager view keeps its upstream style) and the resize handle's style. Its row padding would cancel upstream's indent for the rows under a group header (`.groupHeader~.sessionItem`, 2.1.330+), so the panel indents them itself, to where the header's name starts
9. **`patchStatusDotsCss`** — Appends dot color/animation CSS
10. **`patchSelectionCss`** — Appends the dimmed (not attached) selection chip style
11. **`patchExtensionRemote`** (`remote-bridge/install.ts`, like 12–13) — The webview provider (one per window) is the class with the field `allComms=new Set`, unique in `extension.js`. The field becomes `allComms=(function(p){try{require("./cce-remote/bridge.js").attach(p)}catch(e){…console.error…}})(this)||new Set`: the initializer hands the provider to the bridge while it's constructed (the bridge defers its work), and a missing or failing bridge is only logged. **`installRemoteBridge`** then copies `remote-bridge/bridge.js`, the `.js` files under `lib/` and licence files to `<ext>/cce-remote/` (old copy removed first; plain files only, no symlinks; nothing without a `bridge.js`)
12. **`patchWebviewConnection`** — In `webview/index.js`: both app roots (`X.createRoot(document.querySelector("#root")).render(…{sessions:S…`, chat and Session Manager) become `(window.__cceRemote&&window.__cceRemote.attach(S),X).createRoot(…` (only after `{ , ; )`, so the parenthesis can't turn into a call). In the sessions list: `[__cceConn,__cceSetConn]=useState(!1)` next to its `[TAB,SET]=useState("local")` (picked by the setter the tab buttons call: the MCP server form has a `"local"` state too); the Local/Web row renders for every login (`cce-no-web` hides Web where upstream hid the row), gets `cce-conn-on` while open, closes Connection on a click on another tab (`onClickCapture`), and a third button **Connection**; the list content ``JSX("div",{id:…,className:`${CSS.content} …`,…})`` becomes `__cceConn?JSX("div",{className:CSS.content+" cce-conn",ref:window.__cceRemote.mount},"cce-conn"):…` (keyed, so React mounts a fresh element instead of reusing the list's), and the list root gets `cce-conn-root`. The tab is all or nothing, and only where its state is in scope: the root, the row and the content must sit after the declaration in the block that declares it (bracket-matched by a scanner that skips strings, templates, comments and regex literals), else a `FAIL` line; every read of `__cceConn` and call of `__cceSetConn` is also guarded with `typeof`, so an undeclared name reads as closed instead of throwing (a throw while rendering takes Claude Code's whole view down). The attach is separate, and `Connection runtime attached` fails unless every app root found is hooked. `remote-bridge/webview-runtime.js` is **prepended**: the app boots synchronously at the end of the bundle, and the attach hooks run right then
13. **`patchConnectionCss`** — The tab row's states on the sessions-list module's hashed classes (`cce-conn-on`: Local/Web lose their highlight; `cce-no-web`: no Web tab; `cce-conn-root`: no search row), plus the Connection view's `cce-conn-*` styles (VS Code theme tokens only)

Verify lines for 11–13: `remote bridge hook (extension.js)`, `remote bridge files` (reported apart from the bundle-shape FAILs: it means `remote-bridge/bridge.js` is missing), `Connection tab`, `Connection runtime attached`. `--revert` also deletes `cce-remote/`, turns the Claude in Chrome switch off (`turnChromeAutoAcceptOff`) and, when `~/.cce-remote/state.json` says remote access is on, turns it off there (`enabled:false`) and turns `tailscale serve` off for the bridge's port (`turnRemoteAccessOff` in `install.ts`; 20 s at most, prints the command when it can't; the folder with the pairings stays; with remote access off it doesn't look at serve); `--no-remote` skips 11–13 and deletes a `cce-remote/` left from an earlier run.

After all editors: **`installCommitButton`** (from `claude-commit/install.ts`) installs the commit message button into the same editors, matched by label. It runs even if a patch failed and skips editors whose installed copy is identical *and* still listed in `extensions.json` (an uninstall leaves the folder behind). With `--revert` it uninstalls instead; `--no-commit-button` skips it.

### How patching works

All patches operate on **minified, bundled JS/CSS** via regex and string matching against known code patterns (CSS module variable names, function signatures, `createElement` calls). The script:
- Creates `.bak` backups on first run
- Always reads from `.bak` files (the true originals) so re-running is idempotent
- Each patch function returns `{ patched: string; count: number }` — count tracks how many substitutions were made

### Key pattern-matching strategy

The script finds dynamically-generated CSS class names (e.g., `overlay_abc12`, `dropdown_xyz34`) by matching CSS module object literals in the bundled JS, then uses those class names to locate and modify both JS behavior and CSS rules. This is fragile by nature — extension updates may change the bundle structure.

## claude-commit/ (commit message button)

A plain-CommonJS VS Code extension (`cce-patch.claude-commit-message`, no build step, no dependencies; `.gitignore` re-includes its `*.js`). It mirrors the built-in Copilot commit-message generator (Copilot Chat 0.70 in VS Code Insiders 1.142) and swaps the model call for one `claude -p` call:

- **`lib/context.js`** — Copilot's input: staged changes, else working tree + untracked; per-file diffs (`diffIndexWithHEAD` / synthetic untracked patch / `diffWithHEAD`, cut at 100 000 chars); the last 5 commit subjects from the repo and from `user.name`; current file contents ("ORIGINAL CODE", skipped for new files, and read only while they fit the 300 000-char budget next to the diffs); `github.copilot.chat.commitMessageGeneration.instructions` from all settings scopes (folder → workspace → user, as Copilot merges them), files before texts, language-tagged entries skipped
- **`lib/prompt.js`** — Copilot's prompt texts verbatim (system message, section headings, reminder, instruction intro) in its section structure (XML-style tags, legacy line numbers). One difference: ORIGINAL CODE is a fenced block with a `filepath:` comment, where Copilot uses an attachment tag. Also a 300 000-char budget (largest original code dropped first, then diffs share the rest) and Copilot's ```text block parsing
- **`lib/claude.js`** — finds the CLI (`claudeCommit.claudePath` → the Claude Code extension's `resources/native-binary/claude` → `PATH`). Runs `claude -p --model haiku --safe-mode --tools "" --disable-slash-commands --no-session-persistence --output-format json --settings '{"env":{"CLAUDE_CODE_EFFORT_LEVEL":"low","CLAUDE_CODE_DISABLE_THINKING":"1"}}' --system-prompt …` with the prompt on stdin and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (it halves the latency). Handles cancel and timeout. `--bare` would skip the OAuth/keychain login, so it isn't used. The `--settings` env is there because the CLI applies `env` from `~/.claude/settings.json` even in safe mode, over both the process env and `--effort`: the user's `"CLAUDE_CODE_EFFORT_LEVEL": "max"` made Haiku 5.5 think for 30–40 s on larger diffs (adaptive thinking; only low effort stops it). The thinking variable is for older CLIs, which run Haiku 4.5 with a thinking budget
- **`extension.js`** — the command `claudeCommit.generateCommitMessage`, contributed to `scm/inputBox` (the commit message box) and `scm/title` (fallback). Progress shows in the SCM view, and the result goes to `repository.inputBox.value`
- **`install.ts`** — packs a VSIX (built-in stored-zip writer), installs it with each editor's CLI, and adds the id to `"enable-proposed-api"` in `~/.<editor>/argv.json` (comment-preserving; `--uninstall` reverts). Uses `$(sparkle)` instead of `$(claude)` where the editor lacks that codicon (Cursor). On Windows the CLI is the `.cmd` that `where` lists (after the extensionless WSL shell script), run through cmd.exe with every part quoted (`windowsCommandLine`): the default install path, `…\Programs\Microsoft VS Code\bin`, has spaces

`scm/inputBox` is a proposed menu (`contribSourceControlInputBoxMenu`). Only `product.json`-allowlisted extensions (just Copilot) or ones named in `--enable-proposed-api` / `argv.json` can use it, and `argv.json` applies after a full restart. The extension reads its runtime `packageJSON.enabledApiProposals` (VS Code empties it when the proposal isn't granted) into the context key `claudeCommit.inputBoxButton`. The `scm/title` button hides itself once the box button is live.

Tests: `bun test claude-commit/test`. To verify end to end without touching a running editor, launch an isolated Insiders: `open -g -n -a "Visual Studio Code - Insiders" --args --user-data-dir=<tmp> --extensions-dir=<tmp> --extensionDevelopmentPath=claude-commit --remote-debugging-port=<port> <repo>`. Dev mode grants the proposal. Then drive the button over the Chrome DevTools Protocol.

## remote-bridge/ and remote-app/ (phone remote)

Design and protocol: `docs/superpowers/specs/2026-11-19-phone-remote-design.md` (the plan next to it pins names and tests).

**`remote-bridge/`** runs inside the Claude Code extension host: plain CommonJS (`"use strict"`, only Node built-ins and `vscode`, no dependencies, no build step; `.gitignore` re-includes its `*.js`). `bridge.js` `attach(provider)` taps every webview's comms (`send`, `fromClient`, `processRequest`: the host↔webview protocol), keeps per-session state, and answers the Connection tab's `cce_remote_*` requests. When turned on, the first window binds `127.0.0.1:47821` and becomes the hub, the other windows join it as peers (`Upgrade: cce-peer`; each side proves with an HMAC-SHA256 challenge–response that it knows the secret in `state.json`, which never goes on the wire, and a window that finds a program on the port that can't prove it pauses and keeps `tailscale serve` off), and `tailscale serve` exposes the hub's `/ws` (phones: `Tailscale-User-Login` of the Mac's own user plus a paired device token) on the tailnet; only the last remaining window, closed on its own (the hub with no peer joined, inside the provider's `shutdownAll()`, 2 s budget), turns serve off, and leaves remote access on for the next start. Quitting with two or more windows open stops them together (the hub still has its peers), so serve stays on, as after a crash, until the next start, a Disconnect or `--revert`. State lives in `~/.cce-remote/state.json` (`$CCE_REMOTE_HOME`; 0600), written only when something changes (on/off, a pairing or removal, the app address, a phone's push subscription in `devices[].push`); when a phone was last seen stays in the hub's memory, and while remote access is off the window agents mirror no session messages. Pushes (`lib/notifier.js`, on the hub) go out when a session waits for a prompt (after a 4 s grace) and when a session is done: the window agent's `done` is held back while the channel isn't at rest (the host's `atRest`: a queued prompt or a background task, shells included), while the CLI's last `background_tasks_changed` lists a `local_agent` or `local_workflow` (ambient or not: those keep VS Code's dot blue), and while a prompt is open. It is decided at each `result` (after any word from a task the host isn't at rest again before the next one) and said once, with the last turn's result: a turn that ends with work running in the background ends in a `result` too, so a `result` is not enough on its own, and one for a task notification that ran no turn (`num_turns: 0`) says nothing of its own. A shell left running (a dev server) holds it back for as long as it runs. Claude Code's usage meter (5-hour and weekly limits, 2.1.325+) reaches the phones too: each window agent follows the provider's own `panelUsageRelay` and can have it read afresh through a running session's Claude process (`relayUsageWindowsFromProcess`); the hub sends the newest numbers as a `usage` frame and answers a phone's `usage_refresh` at most once a minute. The frame names the account the numbers belong to (`account`: the email Claude Code got from `claude auth status`, each comms' `cliReportedAccountEmail()`, taken from the same window's reading as the numbers). A phone can ask a window for its slash commands (`commands`): the Claude Code commands VS Code's `/` menu lists, named by `lib/commands.js`. The window agent's `commands()` reads them from what the extension already holds, in this order: a comms' `settledConfig.commands`, its `storedStartupConfig` copy, a running session's `query.supportedCommands()`, then a loading `config`. It never asks the extension to load a config, which can start a Claude process, and the hub bounds the list. Phone messages carry `origin: {kind:"human"}`, as the webview's typed ones do: Claude Code runs a plugin's local commands only from such a message. The Connection tab's Claude in Chrome switch (`chromeAutoAccept: true` in `state.json`; design: `docs/superpowers/specs/2026-11-23-chrome-auto-accept-design.md`) is written by the window itself (`coordinator.setChromeAutoAccept`, request `cce_remote_set_chrome_auto_accept`), never through the hub.
- **Reading it.** `coordinator.chromeAutoAccept()` reads it afresh at every call (`store.chromeAutoAcceptOn`). It fails closed: a missing, unreadable or broken file counts as off. The watcher only logs changes made elsewhere.
- **Wiring.** `bridge.js` points each window agent's `chromeAutoAccept` at it.
- **Answering.** The agent's `_fromHost` swallows a host→webview `tool_permission_request` for a Claude in Chrome tool, meaning `mcp__claude-in-chrome__<tool>` with no `__` in `<tool>`. It does not take one marked for a person: `defaultToNo`, `personOnly`, `reason` or `hookReason`. It answers on the next microtask through the original `fromClient`, unless the host's `outstandingRequests` shows the prompt was withdrawn.
- **What the answer is.** "Always" only when every suggestion is `addRules`/`allow`/`session` for sites (`ClaudeInChromeDomain` with a `ruleContent`); a plain allow otherwise.
- **Visibility.** Neither VS Code nor the phone sees the prompt, unless the answer can't go out.
- **Revert.** `--revert` turns the switch off (`turnChromeAutoAcceptOff` in `install.ts`). Modules in `lib/` (window agent, coordinator, hub, `ws.js`, `peer-link.js`, `store.js`, `pairing.js`, `tailscale.js`, `transcript.js`, `answers.js`, `commands.js`, `qr.js`, `connection-ui.js`, `webpush.js`, `idle.js`, `notifier.js`), as laid out in the spec.

Two files belong to the patcher side and are not copied into the extension:
- **`install.ts`** — patch steps 11–13 above (pure functions, tested on synthetic bundle snippets in `test/fixtures/bundles.ts`, never on extension code), `installRemoteBridge(extDir, srcDir?)`, `removeRemoteBridge(extDir)`, `turnRemoteAccessOff()` (`--revert`: through `lib/store.js` and `lib/tailscale.js`; tests use a temp `CCE_REMOTE_HOME` and the fake Tailscale CLI)
- **`webview-runtime.js`** — the Connection tab's browser code, `window.__cceRemote = {attach(sessions), mount(el|null), request(type, data)}` (plain ES2019, its one global). `request` goes through `sessions.comms.connection.value.sendRequest({type, ...data})`, which resolves with the host's answer (an unhandled type answers `Unknown request type.`, shown as "the bridge isn't running"). While mounted it polls `cce_remote_status` every 2 s (doubling up to 30 s while it fails), redraws only when the status changed, and keeps the app-address input across redraws. A "Claude in Chrome" section below the paired devices turns the switch on or off; it shows only when the status carries `chromeAutoAccept`. The DOM is built with `createElement` (host data only as text and attributes, never `innerHTML`); keys typed in the view don't bubble to the app's handlers unless a modifier is held. Tested against a small fake DOM and clock (`test/fake-dom.ts`)

Tests: `bun test remote-bridge/test` (fake provider and comms, real sockets on random ports, a fake Tailscale CLI through `CCE_REMOTE_TAILSCALE`, `CCE_REMOTE_PORT` for the hub port). Never run `tailscale serve`/`up`/`down` against a real tailnet from tests.

**`remote-app/`** is "CCE Remote", the phone side: a Vite + Preact + TypeScript home-screen web app (exact-pinned dependencies and a lockfile, nothing loaded from third-party origins at runtime) that pairs with a Mac through the Connection tab's code, QR code or link and then talks to its hub over `wss://<mac>.<tailnet>.ts.net:47821/ws`. Built to static files and served by nginx from a Dockerfile on the user's own host, which is inside the trust boundary (it serves the code that holds the device token); both base images are pinned to exact versions, and `CCE_REMOTE_TAILNET` (checked at container start) narrows the CSP's `connect-src` to one tailnet. Only `bad_token`, `bad_origin` and `revoked` make the app stop and ask to pair again; other errors show while it keeps retrying. Typing `/` in the message field lists the window's slash commands (`lib/commands.ts` matches them, `components/SlashCommands.tsx` shows them, the store caches each window's list for 60 s). A tap sends `/name` through the composer's normal send, and after a `/clear`, `/reset` or `/new` the store follows Claude Code into the session it starts. Tests: `cd remote-app && npm ci && bun test test` (`npm run build` type-checks and builds).
